# CortexOps Workbench Design

This document defines the product direction, core workflows, and UI structure
for turning CortexOps into a personal AI PM workbench.

## 1. Product Positioning

CortexOps should become a personal workbench for an AI product manager who is
also growing into a full-stack builder.

Its job is not to collect more information. Its job is to convert external
signals into reviewed priorities, concrete tasks, and portfolio-ready artifacts.

The core loop is:

```text
External sources
-> daily / weekly / monthly automations
-> normalized signal objects
-> JSONL state and pool files
-> manual review
-> candidate pools
-> task board
-> artifacts and retrospectives
```

## 2. Target User

The primary user is an AI PM who needs to:

- track high-signal AI product, engineering, research, and GitHub updates
- make weekly execution decisions instead of passively reading reports
- build demos and portfolio artifacts
- prepare for AI PM interviews, PCD work, and independent builder projects
- manage both CortexOps-generated tasks and unrelated personal work

## 3. Product Principles

1. Judgment before storage: CortexOps should prefer decision-making over
   hoarding links.
2. Manual review is part of the system: human confirmation is a control loop,
   not a failure of automation.
3. Every high-value signal should have a next state: confirm, watch, schedule,
   convert to task, archive, or drop.
4. Weekly and monthly views should prioritize and schedule, not summarize the
   same information again.
5. The UI should feel like an operating console, not a marketing dashboard.
6. JSONL state is the backend contract; Markdown reports are frontend reading
   views.

## 4. Core Objects

### Report

A report is an automation output.

Examples:

- daily AI PM radar
- weekly execution review
- weekly paper radar
- weekly demo recommendation
- weekly engineering learning task
- monthly direction review

Suggested fields:

```text
report_id
report_type
title
date_range
generated_at
source_automation
raw_markdown
summary
status
```

### Signal

A signal is a normalized item extracted from reports or external sources.

The schema should follow `docs/ingestion-normalization.md`:

```text
signal_id
date
title
source_name
source_url
source_type
source_tier
original_format
summary
why_it_matters
tags
priority
confidence
candidate_pool
requires_manual_review
next_action
status
```

### Candidate

A candidate is a signal that has been routed to a pool for possible future
action.

Candidate pools:

```text
product_inspiration
paper_candidate
demo_replication
knowledge_gap
personal_work
archive
drop
```

### Task

A task is an executable item. It can be generated by automations, created from a
signal, or manually added by the user.

Suggested fields:

```text
task_id
title
description
origin
linked_signal_id
linked_report_id
status
priority
due_date
estimated_time
success_criteria
project
tags
created_at
updated_at
```

### Artifact

An artifact is a visible output that can support portfolio, interview, personal
site, or public writing goals.

Examples:

- demo
- README
- product memo
- paper reading note
- architecture diagram
- retrospective
- recording
- portfolio page block

Suggested statuses:

```text
draft
polishing
portfolio_ready
published
archived
```

### Focus Rule

A focus rule is a user-controlled preference that changes how future
automations evaluate and prioritize signals.

Focus rules are defined in `docs/focus-policy.md`.

## 5. Main Workflows

### 5.1 Daily Workflow

Goal: decide what matters today and what action should happen next.

Flow:

```text
Open Today
-> read five-part daily summary
-> read 30-minute reading pack
-> review remaining links that were not selected
-> add any remaining link to the reading pack if needed
-> choose one daily practice from three options
-> confirm or change AI-suggested candidate pools
-> convert selected items into tasks
-> finish or reschedule today's tasks
```

The Today view should show the five-part daily summary first, then the reading
pack, then remaining links. Remaining links should be visible with compact state
labels:

- AI suggested pool
- priority
- reading-pack status
- human review status
- duplicate or material-update reason when a retained item appeared in the
  previous 7 days

When the user adds a remaining link to the reading pack or chooses the formal
daily practice, AI should update the affected JSONL fields and show a short
confirmation summary, such as how many links were added to the reading pack,
which candidate-pool labels changed, and which practice was selected. Confirmed
changes should update the structured state file and the relevant candidate pool
file. The Markdown report is a view, not the state source.

### 5.2 Manual Review Workflow

Goal: turn uncertain automation output into confirmed human judgment.

Flow:

```text
Open Review Inbox
-> inspect signal summary, source, priority, confidence, and suggested pool
-> confirm / change / drop / watch / add to reading pack / convert to task
-> record short rationale when priority changes
```

Key actions:

- Confirm priority
- Change priority
- Change candidate pool
- Add to reading pack
- Mark as watching
- Convert to task
- Convert to artifact candidate
- Archive
- Drop

### 5.3 Candidate Pool Workflow

Goal: keep future options organized without turning everything into tasks.

Flow:

```text
Open Candidate Pools
-> filter by pool, priority, confidence, tag, and age
-> select items for this week
-> schedule, archive, or keep watching
```

Candidate pools should preserve weak signals lightly, but only P0 and strong P1
items should regularly become tasks.

Candidate pool files are the source of truth:

- `pools/product-inspiration.jsonl`
- `pools/paper-candidates.jsonl`
- `pools/demo-replication.jsonl`
- `pools/knowledge-gap.jsonl`
- `pools/personal-work.jsonl`
- `pools/archive.jsonl`

Each pool item should show whether it is pending AI suggestion, confirmed by the
user, changed by the user, or rejected.

### 5.4 Task Workflow

Goal: merge CortexOps-generated work with personal work.

Flow:

```text
Add or import tasks
-> classify into Inbox / This Week / Today / In Progress / Waiting / Done
-> limit active work
-> complete tasks with visible success criteria
```

Suggested statuses:

```text
Inbox
This Week
Today
In Progress
Waiting
Done
Archived
```

### 5.5 Focus Rule Workflow

Goal: let the user change what the system pays attention to before the next
automation run.

Flow:

```text
Open Focus Rules
-> add or edit a focus rule
-> choose source types, tags, target pools, and affected automations
-> set weight and active period
-> preview expected impact
-> save
-> next automation run reads the updated focus policy
```

Example:

```text
Name: GitHub practice fit
Description: Prefer repos that can be tried, lightly replicated, or turned into
an AI PM / indie developer artifact.
Priority boost: high
Source types: github_repo, github_release, github_issue, github_pull_request
Tags: agent, AI coding, eval, memory, workflow, demo, MVP, portfolio
Candidate pool boost: demo_replication, knowledge_gap, personal_work,
product_inspiration
Applies to: daily_radar, weekly_review, demo_recommendation, engineering_learning
Status: active
```

### 5.6 Change Management Workflow

Goal: prevent CortexOps changes from becoming scattered prompt patches.

Flow:

```text
Open Change Protocol
-> define target output contract
-> list required signal fields
-> map source / ingestion / focus policy changes
-> bind affected automations
-> run acceptance checks
-> save or reject the change
```

Every meaningful change should answer:

- What visible output should change?
- Which fields are required to produce it?
- Which policy decides priority, routing, upgrade, or downgrade?
- Which automations emit or consume the change?
- What command or evidence proves the linkage works?

The protocol is defined in `docs/change-protocol.md`.

## 6. UI Navigation

Navigation is two-level: a top horizontal bar with four sections
(Dashboard / Inbox / Library / Settings), and a secondary tab row per section.
The root path `/` redirects to `/dashboard/today`. See
`docs/superpowers/specs/2026-07-03-navigation-restructure-design.md` for the full
rationale and route mapping.

```text
Dashboard (read)      Inbox (curate/triage)   Library (archive)   Settings
  · Today               · Today                 · Reports           · General
  · Weekly              · Candidate Pools       · Artifacts         · Focus Rules
  · Monthly             · Memo
  · Tasks
```

### Dashboard (read / consume)

The reading-oriented command center. AI-selected content is shown first; triage
is never forced here.

- `Today`: five-part daily summary, today's 30-minute reading pack
  (`reading_pack_status=selected`), three daily practice options, active tasks,
  and a non-blocking "N signals waiting to be triaged → Inbox" banner plus an
  optional bottom "quick add" strip for borderline `candidate` links.
- `Weekly`: weekly execution review, paper radar, demo recommendation, and
  engineering-learning report.
- `Monthly`: monthly direction review and how priorities should shift.
- `Tasks`: the unified personal task board (manual + report/signal-derived).

Primary question: What should I read and do today, this week, and this month?

### Inbox (curate / triage)

The place to sort raw inputs. Edits here flow to Dashboard.

- `Today`: today's 30 signals; route to `final_pool`, toggle reading-pack
  membership, confirm / change / drop (no standalone reject). Backlog (non-today)
  pending signals are handled from Candidate Pools via a `human_status=pending`
  filter. Post-triage lifecycle uses `status` (e.g. `watching`, `dropped`).
- `Candidate Pools`: product inspiration, paper candidates, demo replication,
  knowledge gaps, personal work, archive / drop; drag-drop management.
- `Memo`: a lightweight to-do list for questions to confirm later while reading
  reports or building demos (quick-add, check-off, filter; optionally convert to
  a task or a knowledge-gap item). Decoupled from signal import.

Primary question: What needs sorting, and what do I want to remember to look into?

### Library (archive / retrieve)

- `Reports`: historical daily / weekly / monthly reports with a search box.
- `Artifacts`: a high-level portfolio coverage map (topic × maturity) plus a
  portfolio-ready list with external links. Detailed content stays in Obsidian.

Primary question: What did the system generate before, and where is my portfolio
coverage thin?

### Settings (configure)

- `General`: source paths, policy references, import/export, and a **read-only**
  automation runner status panel. Codex remains the runner in Phase 1; the app
  does not call AI directly, so Automations is a reference panel here, not a
  standalone page.
- `Focus Rules`: view, add (via a card form), edit, pause, extend, and archive
  attention rules that change how future automation runs prioritize signals.

Primary question: How is the system configured, and what should it pay attention
to next?

## 7. MVP Scope

The first usable version should focus on:

1. Report reader
2. Review Inbox
3. Focus Rules
4. Candidate Pools
5. Task board

Defer:

- account system
- multi-user collaboration
- complex analytics
- browser extension
- full automation runner UI
- public publishing workflow

## 8. Recommended First Build

The first build should be local-first and data-light.

Recommended stack:

```text
Next.js
TypeScript
Tailwind CSS
shadcn/ui
SQLite
Prisma
```

Start with seeded sample data from current automation prompts and a few manual
sample reports. Add real ingestion only after the core review workflow feels
right.

## 9. Success Criteria

The workbench is successful when the user can:

- read the latest daily or weekly report
- confirm or change signal priority
- route signals to candidate pools
- add a temporary focus rule and see how it affects the next run
- convert a signal into a task
- merge manual tasks with CortexOps-generated tasks
- track at least one artifact from draft to portfolio-ready

## 10. Open Product Questions

1. Should focus rules live only in markdown at first, or should the UI write
   them into a database and export markdown snapshots?
2. Should reports be imported manually first, or should the app read directly
   from automation outputs?
3. Should tasks support calendar dates in MVP, or only Kanban-style statuses?
4. Should Artifacts be part of MVP, or should they come after task workflow is
   stable?
